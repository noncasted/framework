# 0.14.0

4 коммита (`v0.13.1..27e371b9`). У скоупа осталась одна фаза, `IScopeSetup.OnSetup`, синхронная: стадии `BaseSetup` /
`Setup` / `SetupCompletion` / `Loaded`, async-варианты и dispose-фаза удалены (BREAKING для клиента каждой игры). Порядок, который
давали стадии, теперь пишется явно: готовность сервиса - в его конструкторе, всё остальное - ручной вызов в нужной
последовательности у владельца скоупа. Сохранения грузятся явно (`ISaves.Load`, `await builder.AddSaves(...)`). Конец сущности
доходит до слушателей её сервисов раньше, чем освобождаются контейнер и ассеты. Ошибка генератора `CINGR018` ловит `IScopeSetup`,
который не зарегистрирован. Бэкенд: код лобби может вернуться из матча в новое лобби (BREAKING для игр с лобби фреймворка).

## Шаги

### 1. Одна фаза скоупа: `IScopeSetup` (BREAKING)

Кого касается: клиент всех игр. Удалены `IScopeBaseSetup`, `IScopeBaseSetupAsync`, `IScopeSetupAsync`, `IScopeSetupCompletion`,
`IScopeSetupCompletionAsync`, `IScopeLoaded`, `IScopeLoadedAsync`, `IScopeDispose`, `IScopeDisposeAsync`, `ILoadedScope.Initialize()`,
`IEventLoop.RunCustomAwaited`; `IEventLoop.RunConstruct` стал `RunSetup`. Осталось `IScopeSetup.OnSetup(IReadOnlyLifetime)` - один раз
после сборки контейнера, синхронно, по одному, **порядок слушателей ничего не значит**. `IEventLoop.RunCustom<T>` (`IGameStarted`,
`IMetaSetupCompleted`, `ILevelSetup`, ...) не меняется: это событие владельца, момент выбирает он.

Зачем: стадии прятали порядок. Сервис из `SetupCompletion` молча полагался на то, что кто-то в `Setup` что-то приготовил;
async-колбэк мог держать загрузку всего скоупа на запросе к серверу, и это нигде не было написано. Теперь порядок видно в коде.

Три правила вместо стадий (`COMMON_CONTAINER.md` § Setup):

1. **Готов из конструктора.** То, без чего сервисом нельзя пользоваться (своё состояние, объекты, пулы, начальные значения, данные
   уже загруженных сохранений), делается в конструкторе (у MonoBehaviour - в `[Inject]`). Контейнер строит зависимости сервиса раньше
   самого сервиса, поэтому конструктор читает их готовыми, а `OnSetup` любого сервиса может пользоваться любым другим. Lifetime в
   конструкторе - параметр `IReadOnlyLifetime` (lifetime контейнера) или `.WithScopeLifetime()`. Ввода-вывода в конструкторе нет.
2. **`OnSetup` только запускает поведение**: подписки, updater, реакции на значения других сервисов. Он никогда не читает то, что
   готовит `OnSetup` другого сервиса.
3. **Любой другой порядок - ручной явный вызов.** Что должно случиться до сервисов (данные, API платформы) - вызов в инсталлере
   (`await builder.AddSaves(...)`, `SteamApi.Start` в `AddSteam`). Что идёт после загрузки скоупа (цикл игры, старт забега, прогрев,
   который ждёт начало) - вызов владельца после `Load`, в нужной последовательности, в одном месте.

Поиск:
```
git grep -nE "IScopeBaseSetup|IScopeSetupAsync|IScopeSetupCompletion|IScopeLoaded|IScopeDispose|RunCustomAwaited|RunConstruct|OnBaseSetup|OnSetupCompletion|scope\.Initialize\(\)|\bOnLoaded\(IReadOnlyLifetime" -- client/Assets ':!client/Assets/Plugins'
git grep -nE "await \w+\.Initialize\(\);" -- client/Assets ':!client/Assets/Plugins'
```
Второй поиск находит и чужие `Initialize()` (реестры, списки UI): трогать только `ILoadedScope`. Компиляция после обновления указателя
даёт тот же список ошибками - это чек-лист шага.

Сделать: каждое место отнести к одному из случаев ниже, по порядку проверки. Определяет случай не интерфейс, а **читает ли кто-то
то, что сервис готовит в колбэке, и ждёт ли кто-то, пока он закончит**. Найти читателей: `git grep -n "<интерфейс сервиса>"` и
посмотреть, что они делают в своих `OnSetup` / `OnSetupCompletion` / `OnLoaded`.

#### 1.1. Сервисы, зависевшие от порядка стадий -> ручной явный вызов в нужной последовательности

Это главный случай, его нельзя закрыть переименованием. Признаки:
- сервис в `SetupCompletion` / `Loaded` пользуется тем, что другой сервис сделал в `BaseSetup` / `Setup` (мир, созданный в чужом
  `OnSetup`; сущность, заспавненная там же; настройки, применённые раньше);
- два сервиса с побочными эффектами должны выполниться в определённом порядке (сначала собрать арену, потом запустить симуляцию,
  потом стартовать таймер);
- комментарий в коде вида «set up after the scope», «after the setup of X», «IScopeSetupCompletion: the world is created by ...».

Как переписать:
1. Убрать у этих сервисов интерфейсы стадий и регистрации `.As<IScopeBaseSetup>()` / `.As<IScopeSetupCompletion>()` / `.As<IScopeLoaded>()`.
2. Дать каждому публичный метод с понятным именем (`Start(lifetime)`, `Begin(lifetime)`, `Build(lifetime)`), регистрация
   `.AsSelf()` (или интерфейс, если его уже берут другие).
3. Порядок написать **один раз, в одном месте, сверху вниз** - у владельца скоупа после загрузки:
   ```csharp
   var scope = await loader.Load(options);

   // The order of the run: the world first, then what lives in it.
   scope.Resolve<SwarmSimulation>().Start(scope.Lifetime);
   scope.Resolve<ProjectileWorld>().Start(scope.Lifetime);
   scope.Resolve<CoreWorld>().Start(scope.Lifetime);
   ```
   или маленьким композером скоупа, если шагов много (`RunStart`: берёт их зависимостями, `Start(lifetime)` вызывает по порядку,
   регистрируется `.AsSelf()`, владелец зовёт только его).
4. Если зависимость - только «данные готовы» (B читает то, что A посчитал), проще правило 1: A считает это в конструкторе, B берёт A
   зависимостью, явный вызов не нужен (пример: мир `SwarmSimulation` создаётся в его конструкторе, `ProjectileWorld` и `CoreWorld`
   берут его зависимостью и подписываются в `OnSetup`).

Порядок регистраций в инсталлере больше не означает ничего: не полагаться на него и не переставлять регистрации, чтобы «починить»
порядок.

#### 1.2. Сервис готовит состояние для других (`IScopeBaseSetup`, часть `IScopeSetup` / `IScopeSetupAsync`)

Колбэк создаёт объекты, пулы, читает данные, а другие сервисы пользуются ими в своих колбэках или сразу после. Сделать: это - в
конструктор (`[Inject]`), подписки и `_updater.Add` - в `OnSetup`, интерфейс `IScopeSetup`. Образцы фреймворка этого релиза:
`ScreenSafeArea` / `WebSafeArea` (начальное значение в конструкторе), `GlobalCamera` (камера и lifetime в `[Inject]`), `AudioPlayer`
(громкости и пулы в `[Inject]`, updater в `OnSetup`).

#### 1.3. Ничего ни для кого не готовит -> механическая замена

Колбэк только подписывается / добавляет себя в updater, и никто не читает его результат. Сделать: интерфейс -> `IScopeSetup`,
метод -> `OnSetup`, регистрация -> `.As<IScopeSetup>()`. Async-колбэк, который возвращает `UniTask.CompletedTask` (не ждёт ничего), -
так же, синхронно. Работа, которая не должна держать скоуп (подключение через `.Forget()` / `NoAwait`), остаётся запуском из `OnSetup`
без ожидания, её готовность - свойство, которого ждут те, кому надо (так уже сделан `MetaLoop` во всех играх).

#### 1.4. Настоящие ожидания (`IScope*Async`, которые что-то `await`)

Async-фазы нет: загрузка скоупа ждёт только то, что владелец пишет явно. Сделать: публичный `UniTask` метод (`WarmUp(lifetime)`,
`Load(lifetime)`), который **владелец вызывает и ждёт после `Load` скоупа**, перед тем как начать то, что его ждёт:
```csharp
var scope = await loader.Load(options);
await scope.Resolve<RunShaderWarmup>().WarmUp(scope.Lifetime);
scope.Resolve<GamePlayLoop>().Start(scope.Lifetime);
```
Данные, которые нужны сервисам при создании, грузятся до контейнера - асинхронным инсталлером в `Construct` скоупа (как
`AddSaves` в шаге 2): `await builder.AddBookAssets(...)`, затем регистрации.

#### 1.5. `IScopeLoaded` и `ILoadedScope.Initialize()`

- `OnLoaded(lifetime)` -> публичный `Start(lifetime)`, регистрация `.As<IScopeLoaded>()` -> `.AsSelf()`; в загрузчике скоупа
  `await scope.Initialize();` -> `scope.Resolve<GameLoop>().Start(scope.Lifetime);`. Несколько слушателей `Loaded` в одном скоупе -
  вызовы по очереди в нужном порядке (случай 1.1).
- `await scope.Initialize();` скоупа без слушателей `Loaded` (меню, лобби, мета, забег, фон меню, глобальный) - удалить строку.
- Тесты, которые звали `OnLoaded` / `OnBaseSetup` / `OnSetupCompletion` напрямую или `scope.Initialize()`, - новые имена методов /
  явный `Start`.

#### 1.6. `IScopeDispose(Async)`, `RunCustomAwaited`

В играх нет. `IScopeDispose` -> `lifetime.Listen(...)` в `OnSetup`; `RunCustomAwaited` -> цикл по `IReadOnlyList<T>` с `await` у
владельца события.

#### 1.7. Что вычистить после

- Регистрации с удалёнными интерфейсами в инсталлерах (`.As<IScopeBaseSetup>()`, `.As<IScopeSetupAsync>()`,
  `.As<IScopeSetupCompletion>()`, `.As<IScopeLoaded>()`), остатки `using Cysharp.Threading.Tasks` у бывших async-колбэков.
- Поля, которые заполнялись в колбэке и теперь задаются в конструкторе, - `readonly`; поле `_lifetime`, сохранённое только чтобы
  дождаться другой стадии, - убрать.
- Комментарии про стадии («in the base setup», «after the setup completion», «on loaded»): `git grep -niE "base setup|setup completion|BaseSetup|SetupCompletion|OnLoaded|loaded phase|dispose phase" -- client/Assets ':!client/Assets/Plugins'`.
- Доки игры: `git grep -nE "BaseSetup|SetupCompletion|IScopeLoaded|IScopeDispose|Initialize\(\)" -- .claude docs ':!docs/tasks/complete' ':!docs/audits'`
  (`CLAUDE.md`, `.claude/docs`, `CLAUDE_MISTAKES.md` игры): правило из `COMMON_CONTAINER.md` § Setup вместо стадий.
- Ошибка `CINGR018` после сборки: тип реализует `IScopeSetup`, но ни одна его регистрация не перечисляет `IScopeSetup` - его
  `OnSetup` раньше молча не вызывался. Либо `.As<IScopeSetup>()`, либо удалить мёртвый `OnSetup` (проверить, что поведение
  действительно не нужно).
- Настройки игры: тело `OnSetup` / `OnSetupAsync` / `OnSetupCompletion` (`_saves.Get` из уже загруженных сохранений, `Push`, применение
  громкости и языка) - в конструктор. Иначе `AudioPlayer` (громкость читается в его `[Inject]`), `FrameRateLimit`, `RenderResolution`
  (их `OnSetup`) получат значения по умолчанию, а сохранённые придут следом.

### 2. Сохранения загружаются явно: `ISaves.Load()`, `AddSaves` (BREAKING)

Кого касается: клиент игр с `AddItchSaves` (pixel-swarm, mines-leader, peace-data-reborn, neon-dodge), свои реализации и фейки
`ISaves` (neon-dodge: два `FakeSaves` в тестах; storytale-workshop: своя копия `ItchSaves` с `IScopeBaseSetup`). Хранилище читается не в
конструкторе и не в фазе, а в `ISaves.Load()`; его ждёт `AddSaves` модуля `publish` при сборке скоупа (отдельный шаг startup trace,
асинхронное хранилище встанет туда же). `Get` и `Save` до `Load` бросают, второй `Load` бросает.
Поиск: `git grep -nE "AddItchSaves|ISaves\b" -- client/Assets ':!client/Assets/Plugins'`
Сделать:
- `builder.AddItchSaves();` -> `await builder.AddItchSaves();`: инсталлер паблишера (`GlobalPublisherExtensions`) становится
  `async UniTask`, его вызов в `Construct` глобального скоупа - `await`. Без `await` компилятор даёт только предупреждение: проверить.
- Своя реализация `ISaves`: чтение хранилища из конструктора / `OnBaseSetup` - в `public UniTask Load()`, регистрация
  `builder.Register<X>().As<ISaves>()` -> `await builder.AddSaves(new X())`. storytale-workshop может перейти на `AddItchSaves`
  фреймворка, если копия ничем не отличается.
- Фейки `ISaves` в тестах: `public UniTask Load() => UniTask.CompletedTask;`.
- Порядок теперь такой: `AddSaves` (чтение) -> настройки игры читают из памяти в конструкторе (шаг 1.7) -> их потребители.

### 3. Код лобби после матча: `PassToMatch(…, leaderId, userIds)`, `ILobbyCodes.MarkReturned`, `LobbyOptions.ReturnsAfterMatch` (BREAKING)

Кого касается: бэкенд игр с лобби фреймворка (`Game.Lobbies`: pixel-swarm, neon-dodge; у peace-data-reborn своя копия
`LobbyCodeLeases` - не трогать). Код лобби может вернуться из матча в новое лобби того же сервера с тем же кодом: с
`LobbyOptions.ReturnsAfterMatch = true` один раз на матч - при первом игроке, ушедшем из матча насовсем (разрыв с окном переподключения -
не уход), или при закрытии матча - `ILobbyFactory` игры получает `LobbyCreation { Code = тот же, Return = { LobbySessionId,
MatchSessionId, LeaderId } }`, регистр указывает код на новое лобби (`ILobbyCodes.MarkReturned`), места зарезервированы всем игрокам

## Проверить поведение

- Старт: громкость, частота кадров, разрешение и язык сразу берутся из сохранения (не значение по умолчанию на кадр); меню, лобби и
  забег стартуют (`GameLoop.Start` и остальные явные вызовы из шага 1); прогрев шейдеров pixel-swarm заканчивается до начала забега;
  статическая локация peace-data-reborn загружена до старта уровня.
- Конец сущности: слушатели `lifetime.Listen` её сервисов (из `OnSetup`) срабатывают **до** освобождения контейнера сущности и её
  asset groups (раньше - после). Обходы вроде отложенного чтения ассетов в конце сущности можно убрать. Слушатели, которые чужой код
  повесил прямо на lifetime сущности после её загрузки, по-прежнему идут после teardown.
- Битое сохранение itch падает один раз на `Load` (в `AddSaves` при сборке глобального скоупа), а не в конструкторе; блоб остаётся
  под `save_v2_corrupt`, как раньше.
- Сеть: событие объекта, тип которого ещё никто не запросил (`GetEvent<T>`), больше не бросает `Event type ... not found in actions`
  (раньше исключение ловил `NetworkCommandsDispatcher`, событие терялось): `NetworkEvents` держит его в порядке прихода и отдаёт
  первому подписчику источника своего типа (`NetworkEventSource<T>`, первый `Advise` после `GetEvent`), до событий, пришедших позже.
  Предел - `NetworkEvents.MaxPendingEvents = 64` событий без источника на объект, 65-е бросает `InvalidOperationException` с именем
  типа. Правок игр не требует: подписи `INetworkEvents`, `GetEvent`, `InvokeLocal` прежние, источник по-прежнему `ViewableDelegate<T>`.
