# 0.14.0

4 commits (`v0.13.1..27e371b9`). A scope has one phase left, `IScopeSetup.OnSetup`, synchronous: the stages `BaseSetup` /
`Setup` / `SetupCompletion` / `Loaded`, the async variants and the dispose phase are removed (BREAKING for the client of every game). The order the
stages gave is now written explicitly: the readiness of a service is in its constructor, everything else is a manual call in the needed
sequence by the owner of the scope. The saves are loaded explicitly (`ISaves.Load`, `await builder.AddSaves(...)`). The end of an entity
reaches the listeners of its services before the container and the assets are released. The generator error `CINGR018` catches an `IScopeSetup`
that is not registered. Backend: a lobby code may return from a match into a new lobby (BREAKING for games with the lobbies of the framework).

## Steps

### 1. One phase of a scope: `IScopeSetup` (BREAKING)

Who: the client of every game. Removed: `IScopeBaseSetup`, `IScopeBaseSetupAsync`, `IScopeSetupAsync`, `IScopeSetupCompletion`,
`IScopeSetupCompletionAsync`, `IScopeLoaded`, `IScopeLoadedAsync`, `IScopeDispose`, `IScopeDisposeAsync`, `ILoadedScope.Initialize()`,
`IEventLoop.RunCustomAwaited`; `IEventLoop.RunConstruct` became `RunSetup`. What is left is `IScopeSetup.OnSetup(IReadOnlyLifetime)` - once
after the container is built, synchronously, one by one, **the order of the listeners means nothing**. `IEventLoop.RunCustom<T>` (`IGameStarted`,
`IMetaSetupCompleted`, `ILevelSetup`, ...) does not change: it is an event of the owner, the owner chooses the moment.

Why: the stages hid the order. A service of `SetupCompletion` silently relied on someone having prepared something in `Setup`;
an async callback could hold the load of the whole scope on a request to the server, and this was written nowhere. Now the order is visible in the code.

Three rules instead of the stages (`COMMON_CONTAINER.md` § Setup):

1. **Ready from the constructor.** What a service cannot be used without (its own state, objects, pools, initial values, the data
   of already loaded saves) is done in the constructor (in a MonoBehaviour - in `[Inject]`). The container builds the dependencies of a service before
   the service itself, so the constructor reads them ready, and the `OnSetup` of any service may use any other. A lifetime in
   the constructor is an `IReadOnlyLifetime` parameter (the lifetime of the container) or `.WithScopeLifetime()`. No input / output in the constructor.
2. **`OnSetup` only starts behaviour**: subscriptions, the updater, reactions to the values of other services. It never reads what
   the `OnSetup` of another service prepares.
3. **Any other order is a manual explicit call.** What must happen before the services (data, the API of the platform) is a call in the installer
   (`await builder.AddSaves(...)`, `SteamApi.Start` in `AddSteam`). What goes after the load of the scope (the game loop, the start of a run, a warm-up
   that waits for the beginning) is a call of the owner after `Load`, in the needed sequence, in one place.

Search:
```
git grep -nE "IScopeBaseSetup|IScopeSetupAsync|IScopeSetupCompletion|IScopeLoaded|IScopeDispose|RunCustomAwaited|RunConstruct|OnBaseSetup|OnSetupCompletion|scope\.Initialize\(\)|\bOnLoaded\(IReadOnlyLifetime" -- client/Assets ':!client/Assets/Plugins'
git grep -nE "await \w+\.Initialize\(\);" -- client/Assets ':!client/Assets/Plugins'
```
The second search also finds other `Initialize()` calls (registries, UI lists): touch only `ILoadedScope`. The compilation after the pointer is moved
gives the same list as errors - this is the checklist of the step.

Do: assign every place to one of the cases below, in the order of the check. The case is decided not by the interface but by **whether someone reads
what the service prepares in the callback, and whether someone waits until it finishes**. Find the readers: `git grep -n "<the interface of the service>"` and
look at what they do in their `OnSetup` / `OnSetupCompletion` / `OnLoaded`.

#### 1.1. Services that depended on the order of the stages -> a manual explicit call in the needed sequence

This is the main case, it cannot be closed by a rename. Signs:
- a service in `SetupCompletion` / `Loaded` uses what another service did in `BaseSetup` / `Setup` (a world created in another
  `OnSetup`; an entity spawned there; settings applied earlier);
- two services with side effects must run in a certain order (first build the arena, then run the simulation,
  then start the timer);
- a comment in the code like "set up after the scope", "after the setup of X", "IScopeSetupCompletion: the world is created by ...".

How to rewrite:
1. Remove the stage interfaces from these services and the registrations `.As<IScopeBaseSetup>()` / `.As<IScopeSetupCompletion>()` / `.As<IScopeLoaded>()`.
2. Give each a public method with a clear name (`Start(lifetime)`, `Begin(lifetime)`, `Build(lifetime)`), the registration
   `.AsSelf()` (or an interface, if others already take it).
3. Write the order **once, in one place, top to bottom** - by the owner of the scope after the load:
   ```csharp
   var scope = await loader.Load(options);

   // The order of the run: the world first, then what lives in it.
   scope.Resolve<SwarmSimulation>().Start(scope.Lifetime);
   scope.Resolve<ProjectileWorld>().Start(scope.Lifetime);
   scope.Resolve<CoreWorld>().Start(scope.Lifetime);
   ```
   or with a small composer of the scope if there are many steps (`RunStart`: takes them as dependencies, calls `Start(lifetime)` in order,
   is registered `.AsSelf()`, the owner calls only it).
4. If the dependency is only "the data is ready" (B reads what A computed), rule 1 is simpler: A computes it in the constructor, B takes A
   as a dependency, no explicit call is needed (example: the world of `SwarmSimulation` is created in its constructor, `ProjectileWorld` and `CoreWorld`
   take it as a dependency and subscribe in `OnSetup`).

The order of the registrations in an installer no longer means anything: do not rely on it and do not reorder registrations to "fix"
the order.

#### 1.2. A service prepares state for others (`IScopeBaseSetup`, part of `IScopeSetup` / `IScopeSetupAsync`)

The callback creates objects, pools, reads data, and other services use them in their callbacks or right after. Do: this goes into
the constructor (`[Inject]`), subscriptions and `_updater.Add` into `OnSetup`, the interface `IScopeSetup`. Samples of the framework in this release:
`ScreenSafeArea` / `WebSafeArea` (the initial value in the constructor), `GlobalCamera` (the camera and the lifetime in `[Inject]`), `AudioPlayer`
(the volumes and the pools in `[Inject]`, the updater in `OnSetup`).

#### 1.3. Prepares nothing for anyone -> a mechanical replacement

The callback only subscribes / adds itself to the updater, and nobody reads its result. Do: the interface -> `IScopeSetup`,
the method -> `OnSetup`, the registration -> `.As<IScopeSetup>()`. An async callback that returns `UniTask.CompletedTask` (waits for nothing) -
the same, synchronously. Work that must not hold the scope (a connection through `.Forget()` / `NoAwait`) stays a launch from `OnSetup`
without waiting, its readiness is a property waited on by those who need it (`MetaLoop` is already done so in every game).

#### 1.4. Real waits (`IScope*Async` that `await` something)

There is no async phase: the load of a scope waits only for what the owner writes explicitly. Do: a public `UniTask` method (`WarmUp(lifetime)`,
`Load(lifetime)`) that **the owner calls and awaits after the `Load` of the scope**, before starting what waits for it:
```csharp
var scope = await loader.Load(options);
await scope.Resolve<RunShaderWarmup>().WarmUp(scope.Lifetime);
scope.Resolve<GamePlayLoop>().Start(scope.Lifetime);
```
Data the services need when they are created is loaded before the container - by an asynchronous installer in the `Construct` of the scope (like
`AddSaves` in step 2): `await builder.AddBookAssets(...)`, then the registrations.

#### 1.5. `IScopeLoaded` and `ILoadedScope.Initialize()`

- `OnLoaded(lifetime)` -> a public `Start(lifetime)`, the registration `.As<IScopeLoaded>()` -> `.AsSelf()`; in the loader of the scope
  `await scope.Initialize();` -> `scope.Resolve<GameLoop>().Start(scope.Lifetime);`. Several listeners of `Loaded` in one scope -
  calls one after another in the needed order (case 1.1).
- `await scope.Initialize();` of a scope without listeners of `Loaded` (menu, lobby, meta, run, menu background, global) - delete the line.
- Tests that called `OnLoaded` / `OnBaseSetup` / `OnSetupCompletion` directly or `scope.Initialize()` - the new method names /
  an explicit `Start`.

#### 1.6. `IScopeDispose(Async)`, `RunCustomAwaited`

Not in the games. `IScopeDispose` -> `lifetime.Listen(...)` in `OnSetup`; `RunCustomAwaited` -> a loop over `IReadOnlyList<T>` with `await` by
the owner of the event.

#### 1.7. What to clean up after

- Registrations with the removed interfaces in the installers (`.As<IScopeBaseSetup>()`, `.As<IScopeSetupAsync>()`,
  `.As<IScopeSetupCompletion>()`, `.As<IScopeLoaded>()`), leftover `using Cysharp.Threading.Tasks` of former async callbacks.
- Fields that were filled in a callback and are now set in the constructor become `readonly`; a field `_lifetime` kept only to
  wait for another stage is removed.
- Comments about the stages ("in the base setup", "after the setup completion", "on loaded"): `git grep -niE "base setup|setup completion|BaseSetup|SetupCompletion|OnLoaded|loaded phase|dispose phase" -- client/Assets ':!client/Assets/Plugins'`.
- The docs of the game: `git grep -nE "BaseSetup|SetupCompletion|IScopeLoaded|IScopeDispose|Initialize\(\)" -- .claude docs ':!docs/tasks/complete' ':!docs/audits'`
  (`CLAUDE.md`, `.claude/docs`, `CLAUDE_MISTAKES.md` of the game): the rule of `COMMON_CONTAINER.md` § Setup instead of the stages.
- The error `CINGR018` after the build: a type implements `IScopeSetup`, but none of its registrations lists `IScopeSetup` - its
  `OnSetup` was silently not called before. Either `.As<IScopeSetup>()`, or delete the dead `OnSetup` (check that the behaviour
  is really not needed).
- The settings of the game: the body of `OnSetup` / `OnSetupAsync` / `OnSetupCompletion` (`_saves.Get` from the already loaded saves, `Push`, applying
  the volume and the language) goes into the constructor. Otherwise `AudioPlayer` (the volume is read in its `[Inject]`), `FrameRateLimit`, `RenderResolution`
  (their `OnSetup`) get the default values, and the saved ones come after.

### 3. The lobby code after a match: `PassToMatch(…, leaderId, userIds)`, `ILobbyCodes.MarkReturned`, `LobbyOptions.ReturnsAfterMatch` (BREAKING)

Who: the backend of games with the lobbies of the framework (`Game.Lobbies`: pixel-swarm, neon-dodge; peace-data-reborn has its own copy
of `LobbyCodeLeases` - do not touch). A lobby code may return from a match into a new lobby of the same server with the same code: with
`LobbyOptions.ReturnsAfterMatch = true`, once per match - on the first player who left the match for good (a disconnect with a reconnect window
is not a leave), or when the match closes - the `ILobbyFactory` of the game gets `LobbyCreation { Code = the same, Return = { LobbySessionId,
MatchSessionId, LeaderId } }`, the registry points the code to the new lobby (`ILobbyCodes.MarkReturned`), seats are reserved for every player
of the match (`JoinTimeout` of the lobby), the leader is the leader of the match as soon as he has entered (before him - the first one who entered). A refusal of the factory - the code is released,
the match goes on. Without the flag the behaviour is as before.
Search: `git grep -nE "PassToMatch\(|new LobbyCodeLeases\(|: ILobbyCodes\b|new LobbySessionInfo" -- backend`.
Do:
- `ILobbyCodeLeases.PassToMatch(Guid lobbySessionId, ISession match)` -> `PassToMatch(lobbySessionId, match, leaderId, userIds)`:
  the implementation of `ILobbyMatches.Create` of the game (`backend/Game/Global/LobbyMatches.cs`) passes the leader and the users it got.
- `new LobbyCodeLeases(codes, logger)` -> `new LobbyCodeLeases(codes, afterMatch, logger)`: in the test worlds of the game
  (`SessionTestWorld`, `GameTestWorld`) `afterMatch` is `new LobbyCodeRelease()` (the code is released with the match) or `new LobbyReturns(lobbyFactory,
  lobbyOptions, logger)`. In the container of the server `AddSessionHosting` registers the rule by the flag.
- Fakes of `ILobbyCodes` in the tests of the games: a new member `Task MarkReturned(string code, Guid sessionId, Guid returnSessionId)` - the record of the code
  passes to the session `returnSessionId` of the same server without a match; a call by a non-holder of the code throws, like `Release` (the sample is
  `backend/Tests/Hosting/FakeLobbyCodes.cs` of the framework).
- A game that turned the return on (`ReturnsAfterMatch = true`): the lobby factory passes `Return = creation.Return` into `LobbySessionInfo` (without
  this the leader of the returned lobby is the first one who entered) and itself carries over its room properties (mode, arena) from its record of the match
  `Return.MatchSessionId`. Its own fakes of `ILobbyFactory` too.

## Check the behaviour

- Start: the volume, the frame rate, the resolution and the language are taken from the save at once (not the default value for a frame); the menu, the lobby and
  the run start (`GameLoop.Start` and the other explicit calls of step 1); the shader warm-up of pixel-swarm ends before the run begins;
  the static location of peace-data-reborn is loaded before the level starts.
- The end of an entity: the `lifetime.Listen` listeners of its services (from `OnSetup`) fire **before** the container of the entity and its
  asset groups are released (before, after). Workarounds like a deferred read of assets at the end of an entity can be removed. Listeners that other code
  hung straight on the lifetime of the entity after its load still go after the teardown.
- A broken itch save fails once on `Load` (in `AddSaves` while the global scope is built), not in the constructor; the blob stays
  under `save_v2_corrupt`, as before.
- Network: an event of an object whose type nobody has requested yet (`GetEvent<T>`) no longer throws `Event type ... not found in actions`
  (before, `NetworkCommandsDispatcher` caught the exception and the event was lost): `NetworkEvents` holds it in the order of arrival and gives it
  to the first subscriber of the source of its type (`NetworkEventSource<T>`, the first `Advise` after `GetEvent`), before the events that came later.
  The limit is `NetworkEvents.MaxPendingEvents = 64` events without a source per object, the 65th throws `InvalidOperationException` with the name of
  the type. No edits of the games needed: the signatures of `INetworkEvents`, `GetEvent`, `InvokeLocal` are as before, the source is still `ViewableDelegate<T>`.
