# 0.17.0

4 commits (`v0.16.0..adc60eea`). The Roslyn analyzers of the code rules are shipped: `client/core/Analyzers/Framework.Analyzers.dll`
(label `RoslynAnalyzer`, next to `ContainerGenerator.dll`) checks every assembly of a game in the Unity compile and in `dotnet build` of
`client.sln`, FWR001-FWR006 as warnings; third-party code (packages, `Assets/Plugins`) is skipped by its path. The generators of the
framework write `// <auto-generated/>` as the first line, so the analyzers skip their output. A backend takes the same dll in its
`Directory.Build.props`. Also: memory measurements of the deployed backends (`backend/measurements`, tools only).

## Steps

### 1. The analyzers come in the client: third-party code must be where they skip it

Who: every game, client. After the pointer moves the Unity compile and `dotnet build` of `client.sln` print `warning FWR00N` (public
setters, files above 300 lines, several top-level types, Cyrillic in comments, `lock` on a lifetime, a file not named after its type).
Warnings only. The rules and the settings: `client/core/Source~/Analyzers/README.md`.

Search: `ls client/Packages client/Assets/Plugins`

Do:
- Third-party code gets no rule when it is under `Library/PackageCache`, a package folder of `client/Packages` (or the forks in
  `tools/framework/client/packages`) or `Assets/Plugins`. Nothing to add for the packages.
- Unity reads no `.editorconfig`, so third-party code anywhere else in `client/Assets` is moved under `Assets/Plugins` (or marked
  `framework_rules.third_party = true` in `.editorconfig`, which only `dotnet build` honours).

### 2. Regenerate the generated code of the framework

Who: every game, client. Until a file is regenerated the rules see it as code of the game (mines-leader before it: 8 findings in
`Catalogues/Colors/Colors.cs` and `Catalogues/Sprites/CardsIconsSprites.cs`).

Search: `git grep -L '^// <auto-generated/>' -- $(git grep -l 'Auto-generated by' -- 'client/Assets/*.cs')`

Do: `Tools/Framework/Codegen/Regenerate All` (or `-executeMethod Internal.RegenerateAll.Run`). The generators now write
`// <auto-generated/>` as the first line, before `// Auto-generated by X`; after it the search lists nothing. Only the header changes in
the files; revert any other churn of the regeneration (scenes, `_layerAssetGuid` of assets) that is not yours.

### 3. Backend: take the analyzers in `Directory.Build.props`

Who: every game, backend.

Search: `git grep -n 'Framework.Analyzers' -- backend`

Do: add to `backend/Directory.Build.props` (or the props every backend project imports), the path relative to the props file:

```xml
<ItemGroup>
  <Analyzer Include="$(MSBuildThisFileDirectory)../tools/framework/client/core/Analyzers/Framework.Analyzers.dll" />
</ItemGroup>
```

Then build `backend/backend.slnx`: the warnings of the backend of the game and of the framework backend appear, nothing fails.

### 4. Count the findings and set the severities

Who: every game.

Search: `dotnet build client/client.sln -v:minimal | grep -oE 'warning FWR[0-9]+' | sort | uniq -c` (each warning is printed twice,
divide by two), the same for `backend/backend.slnx`.

Do: plan the cleanup from the counts. In the `.editorconfig` of the game a rule it is not ready for may be
`dotnet_diagnostic.FWR00N.severity = none`, a rule with no findings in the code of the game may become `error`. Both work in `dotnet build`
only: in the Unity compile every rule stays a warning.

## Check the behaviour

- The Unity compile and `dotnet build` print new warnings `FWR00N`; nothing else changes at runtime.
- A changed analyzer dll recompiles every assembly: the first compile after the update is long.
