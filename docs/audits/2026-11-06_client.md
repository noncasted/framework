### K2. `FrameRateLimit`: авто-режим не останавливается при выборе фиксированного и запускается дважды (ложная)

- Где: `client/modules/framerate/Runtime/FrameRateLimit.cs:44-71`, `Auto/AutoFrameRate.cs:29-35`,

  пороге перезаписывает выбор игрока (`Apply("auto", …)`). При смене обратно на Auto `Run` вызывается второй раз:

- Как исправить: завести отдельный `ILifetime` авто-режима (`lifetime.Child()`), завершать его при уходе из Auto, а
  `AutoFrameRate.Run` либо сделать идемпотентным, либо запретить повторный вызов. Тест: Auto → Low → истечение
  `DropSeconds`/`RiseSeconds` — лимит остаётся выбранным; Auto → Low → Auto — один апдейт.
- Проверка: ложная. `Choose` получает от `IViewableProperty.View(lifetime, Action<IReadOnlyLifetime, T>)` не lifetime скоупа,

## Важные

### K1. Две экземплярные регистрации одного типа в ветвях одного `if` роняют построение scope (понижена из критичных)
- Где: `client/core/Source~/ContainerGenerator/Scope/RegistrationOccurrences.cs:10-20`, `Scope/Plan/PlanHoles.cs:42-48`,
  `Scope/Emit/RegisterWriter.cs:81-90`; следствие — `client/core/Runtime/Tools/Container/Runtime/ScopeRegistrations.cs:84-100`,
  `ContainerCoverage.cs:35-55`
- Правило: баг
- Проблема: `InstanceOccurrence` считает экземплярные регистрации в порядке написания, не исключая ветви одного оператора
  (`ConstructedOccurrence` и `ArmOccurrence` в этом же файле `BranchGroups.Exclude` используют). Для
  `if (isEditor) builder.RegisterInstance<IClock>(editorClock); else builder.RegisterInstance<IClock>(playerClock);`
  ветвь `else` получает occurrence 1, а builder выполняет только одну ветвь и содержит один экземпляр. Сгенерированный
  конструктор вызывает `request.GetInstance<IClock>(1)` и бросает `InvalidOperationException` «has 1 instance(s) …
  expects at least 2». Проверка `ContainerCoverage` это пропускает: `ShapeInstances` пишет в массив тип на каждый слот
  (`1 > 2` ложно). Тот же крэш даёт `try { RegisterInstance(a); } catch { RegisterInstance(b); }`: `StatementWalker`
  не размечает ветви try/catch вовсе.
- Как исправить: в `InstanceOccurrence` добавить условие `BranchGroups.Exclude(other, registration) == false` (как в
  `ConstructedOccurrence`), а в `ContainerCoverage` сравнивать зарегистрированные экземпляры с числом слотов, до которых
  реально дошло выполнение. Регрессионный сценарий: `if (flag) RegisterInstance<IClock>(a); else RegisterInstance<IClock>(b);`
  с потребителем `IClock`, прогон обеих ветвей.
- Проверка: подтверждена экспериментом. Сценарий `if/else` с двумя `RegisterInstance<IClock>` падает с «has 1 instance(s) of
  Sample.IClock, the generated class expects at least 2». Понижена до важной: падает сразу при сборке scope, сообщение
  понятное, тихой порчи нет. Два отдельных `if` без `else` — заявленное ограничение генератора (о нём говорит текст ошибки).

### R1. `AssetGroup.Load` оставляет `Retain` ждать навсегда, если выгрузка бросила (понижена до мелкой)
- Где: `client/core/Runtime/Catalogues/Shared/AssetGroup.cs:128-171` (catch 141-148, успешная ветвь 160-168)
- Правило: баг, P8, «await, который не заканчивается»
- Проблема: `UniTaskCompletionSource` завершается после побочного эффекта. В catch: `_loading = null` → `UnloadFailedGroup()`
  → только затем `loading.TrySetException`. Если `UnloadGroup` бросит (в форке Addressables
  `AsyncOperationBase.DecrementReferenceCount` бросает «already 0», а `AssetGroup<T>.UnloadAsset` вызывает её), ожидающие
  в `Retain` не получают ни результата, ни ошибки; исключение уходит в необработанный UniTask. Та же ошибка в ветке
  «отпустили до конца загрузки»: `UnloadGroup()` до `TrySetResult()`. Сценарий: прелоад группы упал на кривом хендле,
  `InvokeBeforeBuild` скоупа висит вечно.
- Как исправить: завершать источник первым либо в `finally`: `try { UnloadFailedGroup(); } finally { loading.TrySetException(e); }`;
  в успешной ветке — `try { UnloadGroup(); } finally { loading.TrySetResult(); }`.
- Проверка: механизм подтверждён чтением кода, но случай пограничный — мелкая.

### R2. `EntityScopeLoader` вызывает `RunLoaded` на уже уничтоженном контейнере
- Где: `client/core/Runtime/Scopes/Entities/EntityScopeLoader.cs:104-138` (проверка токена 112, `RunConstruct` 131,
  `IsConstructed = true` 132, `RunLoaded` 135); teardown — `:140-172`

  в начале `Load`.
