### RES-1 CONFIRMED
- Severity: important (was important)
- Evidence: reading (plus byte inspection of the real build `/var/tmp/ps-wpt23/builds/website/index.html`)
- Why: `BuiltPageScripts.Inject` matches only the `<head>` open tag and inserts the whole script at `head.Index + head.Length`, i.e. before everything the template put in the head. `RenderResolutionInjection` is an unconditional `IPostprocessBuildWithReport` for WebGL builds (the helper's early return only skips non-WebGL), and `render-resolution.js` is 6257 bytes, so the template's `<meta charset="utf-8">` (byte 48 in the template) ends up at byte 9217 in the real build — beyond the 1024-byte window of the HTML encoding prescan, so the declaration is ignored. The page has no BOM (`b'<!D'`), and the deployed nginx (`/var/tmp/ps-wpt23/client/deploy/nginx.conf`, the file the finding means; the framework itself has no `client/deploy`) sets no `charset` directive and the `location = /index.html` block only adds `Cache-Control`, so `index.html` goes out as bare `text/html`. The bug is currently latent only because all three pixel-swarm templates are pure ASCII (0 non-ASCII bytes in the built page and templates); any Cyrillic title/loading text in a template decodes as the locale fallback (windows-1252/windows-1251) and turns to mojibake. Note the charset displacement already existed before the resolution script (the `website-before` build has it at byte 2918 from `startup-trace.js` alone), so the root cause is the helper's insertion point, as the fix states.
- Lines: `client/core/Editor/Tools/Build/BuiltPageScripts.cs:18` - `<head(\s[^>]*)?>` matched at the open tag only; nothing about `<meta>`
- `client/core/Editor/Tools/Build/BuiltPageScripts.cs:38-40` - the tag is inserted at `head.Index + head.Length`, before all template head content including `<meta charset>`
- `client/modules/resolution/Editor/RenderResolutionInjection.cs:16-19` - `OnPostprocessBuild` calls `InjectIntoBuild` for every WebGL build
- `client/modules/resolution/WebTemplate~/render-resolution.js` - 6257 bytes, so the charset is pushed past the 1024-byte prescan window
- `/var/tmp/ps-wpt23/builds/website/index.html:238` - `<meta charset="utf-8">` at byte 9217 (line 238), 0 non-ASCII bytes, no BOM
- `/var/tmp/ps-wpt23/client/Assets/WebGLTemplates/Default/index.html:5` - template's charset at byte 48
- `/var/tmp/ps-wpt23/client/deploy/nginx.conf` - no `charset` directive, `index.html` served with `Cache-Control` only
- Run: none (reading; the real build artifact was inspected byte-wise: `d.lower().find(b'<meta charset') == 9217`, `d[:3] == b'<!D'`)
- Fix check: Right. Inserting after the last `<meta>` that precedes the first `<script`/`<link` keeps the injected script ahead of all template scripts while leaving the charset declaration inside the prescan window; a fallback to just after `<head>` when no charset meta exists is needed too (the current unit test's HTML has no meta). Extending `RenderResolutionScriptTests.Inject_BeforeTheScriptsOfTheTemplate` with a `<meta charset>` in the fixture and asserting both "before `web-shell.js`" and "charset within the first 1024 bytes" is the correct regression guard; a test on the helper itself (`BuiltPageScripts` has no test of its own) would be even better since `telemetry` and `platforms/web` share the same code path.
