### RES-3 FALSE
- Severity: minor (was minor)
- Evidence: reading
- Why: The premise that the key names a *game's* shell, left over from pixel-swarm, is refuted by the framework's own `web` platform: `window.webShell` is the framework's page-shell contract ("safe area, mobile check" of `TemplateData/web-shell.js`), declared and required by `client/platforms/web` (`WebShell.cs`, `WebShell.jslib` "Every template has to load it", `WebExtensions.cs`, the package description), so `webShell.resolution` is the framework platform's namespace, not a game feature — P14 ("a utility knows no feature") does not apply. Keeping the identical key is not an oversight but a documented, deliberate migration decision made when the script was moved out of the shell: the script's own comment says "a mode picked before the move is kept", the design handoff says "same formula, same localStorage key `webShell.resolution`", `releases/unreleased.md` writes "ключ `webShell.resolution` в localStorage сохранён" into the update steps for every game, and the test pins it. The storage read is already inside the boundary `try/catch`; the throw on an unknown value is the repo's written fail-fast rule (ARCHITECTURE_PRINCIPLES 8) and fires only on a foreign value under this exact key (manual devtools edit / another app reusing the key), and the key mirrors the game's save on every `set` (`RenderResolution.Apply` on setup completion), so the save and the key cannot disagree unless another writer on the same origin touches it. The cross-origin sharing is real in principle, but it needs two framework games on one origin and self-corrects on the first `set` — and the finding's own fix would not change it (see Fix check), so the finding as filed is not a rule violation.

- Fix check: The proposed fix is wrong on both stated harms. A "framework-owned" key (`framework.resolution`) is still per-origin, so it would make *every* framework game on one origin share the mode — generalizing, not fixing, the cross-game crosstalk; only the per-game `key` argument it mentions as an alternative would, and that is a deployment choice P14 does not demand. And the rename leaves `storedMode`'s throw untouched, so the `window.renderResolution === undefined` load failure on a foreign value would persist. If the residue is to be addressed, keep the key (the announced decision) and treat an unknown stored value as "auto" with a console warning (an input the page cannot control), or, for the crosstalk, hand the key in from the template — not a rename.
