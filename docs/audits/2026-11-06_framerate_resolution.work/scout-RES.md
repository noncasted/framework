### RES-1 The injected script lands before `<meta charset>`, so the built page loses its encoding
- Where: `client/modules/resolution/Editor/RenderResolutionInjection.cs:18` (and `client/core/Editor/Tools/Build/BuiltPageScripts.cs:33-40`, the helper it calls)
- Rule: bug
- Severity: important
- Evidence: reading (verified on a real build: `<meta charset>` at byte 9217)
- Claim: `BuiltPageScripts.Inject` inserts the whole script immediately after the `<head>` open tag. `render-resolution.js` is 6257 bytes, so on its own it pushes `<meta charset>` past the ~6.3 KB mark; together with `startup-trace.js` (2383 bytes) the real build `/var/tmp/ps-wpt23/builds/website/index.html` has the charset declaration at byte 9217 (line 238). The HTML encoding prescan only reads the first 1024 bytes, so the built page carries no encoding declaration at all. Unless the deploy server sends `charset` in the `Content-Type` header (the framework's `client/deploy/nginx.conf` sets no `charset` directive, so `index.html` goes out as `text/html` without one), the browser falls back to windows-1252 and every non-ASCII character of the template (a Cyrillic `{{{ PRODUCT_NAME }}}` in `<title>`, loading text, the rotate cover) renders as mojibake. Before the move the resolution code sat in `TemplateData/web-shell.js`, loaded after the metas, so this package's injection is what introduces it here; `audio-session.js` (411 bytes) alone stays under the limit, `startup-trace.js` does not.
- Scenario: a game whose template has Russian title or loading text is built and deployed to a server without a charset header (the framework's nginx); the tab title and the loading screen show mojibake, `document.characterSet` is windows-1252 for the whole page. For an ASCII-only template (pixel-swarm today) it is latent.
- Proof lines: `client/core/Editor/Tools/Build/BuiltPageScripts.cs:33` - the head is matched at the open tag only; `BuiltPageScripts.cs:38-40` - the tag is inserted at `head.Index + head.Length`, i.e. before everything the template put in the head; `client/modules/resolution/Editor/RenderResolutionInjection.cs:18` - the injection is unconditional for every WebGL build; `WebTemplate~/render-resolution.js:1-30` - 6.2 KB of script that now precedes the charset; `/var/tmp/ps-wpt23/builds/website/index.html:238` - a real build with `<meta charset>` on line 238, byte 9217.
- Could be wrong if: the server sends `Content-Type: text/html; charset=utf-8` (then the header wins and the position is harmless - checked the framework nginx: it does not), or if no game template ever has non-ASCII text (pixel-swarm's is ASCII, mines-leader/peace-data-reborn only have non-ASCII comments, so the effect is latent today).
- Fix: in `BuiltPageScripts.Inject` insert after the last `<meta>` that precedes the first `<script`/`<link` (or explicitly after the charset meta), keeping the script ahead of the template's scripts; extend `RenderResolutionScriptTests.Inject_BeforeTheScriptsOfTheTemplate` to assert the script is inserted before `TemplateData/web-shell.js` **and** that `<meta charset>` stays within the first 1024 bytes.

### RES-2 The `maxRatio` constraint in the script header is stated backwards
- Where: `client/modules/resolution/WebTemplate~/render-resolution.js:9-10` against `:95-97`
- Rule: `CODE_STYLE_FULL § Comments` (a comment states a constraint the code cannot)
- Severity: minor
- Evidence: reading
- Claim: The header says "low takes k up to device / maxRatio", i.e. k ≤ device/maxRatio and therefore the render ratio ≥ maxRatio; the code does `Math.ceil(device / maxRatio - 1e-6)`, i.e. k ≥ device/maxRatio, so that the ratio stays ≤ maxRatio - the opposite direction, and the one the parameter name and the header's own example ("maxRatio 1 there: 820x360", ratio 0.9167 < 1) describe. A game author picking a tag from the comment sets it the wrong way; with `MOBILE_MAX_PIXEL_RATIO = 1` (which pixel-swarm's build profiles use today) the canvas comes out *smaller* than the CSS size (820 for 895 CSS px at 2.75) and the browser upscales it - the opposite of what "k up to device / maxRatio" lets one believe. The same header also says `?dpr=<number>` "replaces maxRatio of the low resolution", while the code applies it in `high` mode too: `?dpr=2` on a 2.75 phone in High renders at 1.375 instead of 2.75, so that diagnostic silently stops testing High.
- Scenario: a game reads the header, sets the tag to 1 expecting "never below the CSS resolution" (k capped at 2.75), and ships a phone build rendered at 0.92 of the CSS size; or an A/B run with `?dpr=2` believes it measured High.
- Proof lines: `WebTemplate~/render-resolution.js:9` - "k up to device / maxRatio"; `WebTemplate~/render-resolution.js:95` - `Math.ceil(device / maxRatio - 1e-6)` takes k from device/maxRatio up; `WebTemplate~/render-resolution.js:97` - the ratio is `device / k` (so it is at most maxRatio, not at least); `WebTemplate~/render-resolution.js:18-19` - the `?dpr` sentence; `WebTemplate~/render-resolution.js:84-89` - the `else if (isHigh())` is skipped whenever `?dpr` is present, so High is capped.
- Could be wrong if: `maxRatio` is meant as a minimum ratio, despite its name, the header's example and the tests (`[TestCase(Android, "low", "", 1d, 2.75d / 3d)]` asserts k = 3 at maxRatio 1) - checked all three, they say maximum.
- Fix: reword to "k from device / maxRatio up, the smallest k that keeps the render ratio at most maxRatio and the visible short side at least 360", and state that `?dpr=<n>` caps the ratio in every mode, including High.

### RES-3 A framework script hardcodes a game shell's localStorage key
- Where: `client/modules/resolution/WebTemplate~/render-resolution.js:32` (`const storageKey = "webShell.resolution"`), used at `:45`, `:53`, `:65`
- Rule: `P14` (a shared utility knows no feature) - the key names the game's web shell, which the module no longer uses
- Severity: minor
- Evidence: reading
- Claim: `render-resolution.js` is injected into the WebGL build of every game and reads/writes the key `webShell.resolution` of pixel-swarm's old shell. The key is per origin, not per game: two games of the framework served from one origin (a studio domain with `/a` and `/b`, a platform hosting many games) share the stored mode, so game B's first start builds its canvas at the mode last chosen in game A - `pixelRatio` runs before `createUnityInstance` - and its own C# then applies B's saved mode, resizing the drawing buffer in the first seconds (the same pop happens within one game whenever the save and the key disagree, e.g. after a "reset settings"). Worse, `storedMode` throws on any value outside `auto/low/high` during the head script: `window.renderResolution` is then never assigned, the template's `renderResolution.pixelRatio(...)` throws in the same script and the game does not start - a failure caused by data another app on the origin wrote.
- Scenario: two framework games on `games.example.com/a` and `/b`; the player sets Low in A, opens B (saved High) and sees B build a low buffer and jump back a moment later. A non-framework page of the same origin that stored `"2"` under that key makes the game fail at load with "renderResolution is undefined" on top of the real error.
- Proof lines: `WebTemplate~/render-resolution.js:32` - a fixed key named after the game shell; `:45` - read at script load, before anything of the page runs; `:53` - an unknown stored value throws out of the IIFE, leaving `window.renderResolution` undefined; `:65` - the same fixed key is written on every setting.
- Could be wrong if: every game always gets its own origin, so no two pages share the key and no foreign writer exists - then it only costs the name; the key is deliberately kept for pixel-swarm's migration (`releases/unreleased.md`), which explains the value but not sharing it with every other game.
- Fix: use a framework-owned key (e.g. `framework.resolution`) and read `webShell.resolution` once as a migration fallback; if a game must keep its own key, take it as an argument (`renderResolution.pixelRatio(canvas, max, key)` / `follow(module, canvas, max, key)`) the template passes.
