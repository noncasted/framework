# Hierarchy Bindings

**TL;DR:** a prefab or scene object gets a generated `*Bindings` MonoBehaviour that mirrors its hierarchy as typed, serialized references (`bindings.WeaponSocket.Left.Transform`). Gameplay code is plain classes that take the bindings in the constructor; nothing searches the hierarchy at runtime (`transform.Find`, `GetComponentInChildren`) and nothing else is a MonoBehaviour on entity prefabs.

Code:
- Runtime: `tools/framework/client/core/Runtime/Tools/HierarchyBindings/` (`ObjectBindings`, `IObjectBindings`, `HierarchyBindingsIgnoreChildren`)
- Editor generator: `tools/framework/client/core/Editor/Tools/HierarchyBindings/`
- Generated files: `<Module>/Assets/Generated/*Bindings.g.cs` of the assembly that owns the object, e.g. `client/Assets/GamePlay/Assets/Generated/PlayerBindings.g.cs`, `client/Assets/Menu/Assets/Generated/LobbyBindings.g.cs`

## What Is Generated

```csharp
// Auto-generated by HierarchyBindingsGenerator. Do not edit manually.
namespace GamePlay.Players {
    // Structure: c7a6f12a86ed9890fb8652a4b1b63fc5
    // Player
    //   - Body
    //   - WeaponSocket
    //       - Left
    //       - Right
    [DisallowMultipleComponent]
    public class PlayerBindings : global::Internal.ObjectBindings, global::Internal.IEntityComponent
    {
        [SerializeField, HideInInspector] private global::UnityEngine.Transform _transform;
        [SerializeField, HideInInspector] private WeaponSocketBindings _weaponSocket;

        public global::UnityEngine.Transform Transform => _transform;
        public WeaponSocketBindings WeaponSocket => _weaponSocket;

        public virtual void Register(global::Internal.IEntityBuilder builder)
        {
            global::Internal.BuilderExtensions.RegisterComponent(builder, this);
        }

        [Serializable]
        public sealed class WeaponSocketBindings { /* GameObject, Transform, Left, Right ... */ }
    }
}
```

- Every object gets `GameObject`, `Transform` and one property per component; every child becomes a nested `[Serializable]` class.
- Three or more consecutive siblings with the same base name (`Entry`, `Entry (1)`, `Entry_2`) and the same content collapse into an array with a plural name (`MinGroupSize = 3`); two siblings stay separate (`Left` / `Right`).
- A child that has its own bindings component is a boundary: the parent references that component and does not descend.
- `HierarchyBindingsIgnoreChildren` on an object keeps the object but cuts its children (scroll contents, spawn roots).
- Unity serializes nested non-Object types only 7 levels deep (`MaxNestingDepth = 7`); deeper parts need their own bindings component.
- Names come from object and component names converted to C# identifiers; names that clash with `MonoBehaviour` members are renamed (otherwise CS0108 appears in a user file).
- The `Structure:` hash is stored in `ObjectBindings._structureHash`: the snapshot of the hierarchy at generation time.

Registration flags (stored on the component, `ObjectBindings.IsSceneService` / `IsEntityComponent`, reused by Regenerate):

| Flag | Generated | Used by |
|------|-----------|---------|
| Scene service | `ISceneService.Create(IScopeBuilder)` registering the component | scenes with `SceneServicesFactory` (see `COMMON_CONTAINER.md`) |
| Entity component | `IEntityComponent.Register(IEntityBuilder)` registering the component | prefabs with a `ScopeEntityView` subclass (see `ENTITIES.md`) |

The methods are `virtual`: a user class may inherit the generated class and extend the registration. The generated type is the class directly under `ObjectBindings`.

## Using Bindings

```csharp
// client/Assets/GamePlay/Players/Entity/Components/Weapons/PlayerWeaponSocket.cs
public class PlayerWeaponSocket : IPlayerWeaponSocket
{
    public PlayerWeaponSocket(PlayerBindings bindings)
    {
        var socket = bindings.WeaponSocket;
        _center = socket.Transform;
        _left = socket.Left.Transform;
        _right = socket.Right.Transform;
    }
}
```

`ScopeEntityView` keeps a serialized list of the `IEntityComponent`s under it (filled in `OnValidate` / the `Scan` button) and calls `Register` on each when the entity scope is built, so the bindings are resolvable by their concrete type inside the entity scope.

## Generating and Regenerating

Generation is two-phase because a domain reload happens in between: the class is written, scripts recompile, then the component is added to the object and its references are filled. The pending request lives in `SessionState` (`HierarchyBindingsRequest`).

- First time: select the object, `GameObject/Create Object Bindings` or `Tools/Object Bindings/Create For Selection` opens `HierarchyBindingsWindow` (name, namespace, flags, Generate). The class goes to the `Generated` folder of the assembly of the first project script on the object, or of the nearest asmdef above the asset.
- After a hierarchy change: the same window shows Regenerate; for a whole scene `Tools/Project Tools` (Ctrl+G), tab Current Scene, button Regenerate All Bindings (`HierarchyBindingsBatch.RegenerateScene`: all classes are written first, then one refresh). Save the scene first: binding after the reload works with what is on disk.
- Whole project: `Tools/Framework/Codegen/Regenerate All` writes the code of the bindings of every prefab asset and of the loaded scenes, and binds again only those whose code changed, whose structure hash is stale or which hold an empty reference (see `CODEGEN.md`).
- From code (MCP `execute_code`, works on a prefab asset): `Internal.HierarchyBindingsGenerator.Generate(prefabAsset, "Name", "Namespace", isSceneService, isEntityComponent)`, or `HierarchyBindingsGenerator.Regenerate(bindingsComponent)`.

From MCP (`execute_code`, no window): `HierarchyBindingsGenerator.Prepare(root, type.Name, type.Namespace, flags, out var changed)` for each prefab asset root (`ResolveGeneratedType` of its `ObjectBindings` gives the type), then `Flush(changed)`. The binding phase runs on `EditorApplication.delayCall`, which does not fire while the editor window is unfocused: after the reload call the private static `ProcessPending` by reflection and check that the new references are filled and `StructureHash` changed.

Rules:
- Never edit `*Bindings.g.cs` by hand except to unblock a compile deadlock (see `CODEGEN.md`, namespace rename).
- One bindings class per object type: two owners of the same class name would overwrite each other's file.
- The namespace of a generated class follows its owner view; moving the owner to another namespace means regenerating the bindings.
- After changing a prefab hierarchy used by an entity, regenerate the bindings, then rescan the `ScopeEntityView` list and let the container asset map refresh (CINGR006/CINGR003 otherwise, see `COMMON_CONTAINER.md`).

## Runtime Views Come From Prefabs

A runtime object comes from a prefab: a composite view from the children of an entity prefab through its bindings,
many short-lived copies from a pool over a template prefab. `new GameObject` / `AddComponent` stay in editor builders
and tests. The pools, templates and roots are assets of the game: its docs describe them.
